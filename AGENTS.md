# AGENTS.md — протокол работы над shortEditor

Этот файл обязателен к прочтению любым ИИ-агентом (и человеком), который берётся за проект.
Цель протокола: если один агент прервался на середине задачи, следующий вошёл в курс дела за 5 минут и продолжил без потери контекста.

---

## 1. Порядок чтения при старте

1. `AGENTS.md` — этот файл (правила).
2. `docs/HANDOFF.md` — где мы сейчас, что сломано, какая задача следующая.
3. `docs/TASKS.md` — доска задач и история.
4. `docs/SPEC.md` — что вообще требуется.
5. `docs/ARCHITECTURE.md` — карта модулей.
6. `docs/DECISIONS.md` — почему сделано именно так (не переделывай без причины).

Не начинай писать код, пока не прочитал 1–3.

---

## 2. Где правда о состоянии проекта

| Вопрос | Источник |
|---|---|
| Что делаем и зачем | `docs/SPEC.md` |
| В каком состоянии проект | `docs/HANDOFF.md` |
| Какая задача свободна / кто чем занят | `docs/TASKS.md` |
| Почему так спроектировано | `docs/DECISIONS.md` |
| Как разложен код | `docs/ARCHITECTURE.md` |

SQLite в рантайме — источник истины по клипам; журналы в `docs/` — источник истины по разработке. Не путать.

---

## 3. Правила взятия задачи

1. Выбирай задачу со статусом `todo`, у которой выполнены все `depends on`, либо задачу, явно назначенную тебе пользователем.
2. Перед началом работы **в том же коммите** переведи её в `in_progress` и укажи себя: `owner: <имя агента/сессии>, YYYY-MM-DD`.
3. Не трогай задачи со статусом `in_progress` другого владельца. Если нужно вмешаться — сначала зафиксируй в `docs/HANDOFF.md`, что именно и почему.
4. Одна задача — одна ветка и один PR (или один логический набор коммитов, если работаешь напрямую).
5. Задача считается `done` только при выполнении **всех** критериев приёмки и зелёных тестах/линтере.

## 4. Правила завершения сессии (обязательно)

Перед тем как закончить работу — даже если задача не доделана:

1. Обнови статус задачи в `docs/TASKS.md` (`in_progress` / `blocked` / `review` / `done`).
2. Допиши запись в раздел «История» `docs/TASKS.md` (append-only):
   `YYYY-MM-DD · <ID> · <агент> · что сделано · что осталось · следующий шаг`.
3. Перепиши `docs/HANDOFF.md`: текущая ветка, что работает, что не работает, где остановился, какой файл открывать первым.
4. Если принял нетривиальное решение — добавь ADR в `docs/DECISIONS.md`.
5. Закоммить изменения журналов отдельным коммитом `docs: handoff after <ID>`.

Если сессия обрывается без этих шагов — следующий агент обязан начать с `git status` и `git diff`, восстановить картину и **сначала** привести журналы в соответствие с кодом.

## 5. Формат задач

```
### S1-03 · Docker-образ и compose
- status: todo
- owner: —
- depends on: S1-01, S1-02
- area: docker/, pyproject.toml
- acceptance:
  - [ ] ...
```

ID: `S<этап>-<номер>`, сквозной и неизменяемый. Не переиспользуй ID удалённых задач.

Статусы: `todo` → `in_progress` → (`blocked`) → `review` → `done`.

## 6. Коммиты и ветки

- Ветка: `task/S1-03-docker-compose` или `fix/<кратко>`.
- Коммит: `<ID>: <императив, что сделано>` — например `S1-02: add clip status state machine`.
- Документация: `docs: ...`.
- Никаких секретов в коммитах: только `.env.example`.
- Не коммить `data/`, `downloads/`, модели Whisper, `.env`.

## 7. Технические ограничения проекта (не нарушать без ADR)

- Python 3.11+, async-first (aiogram 3, aiosqlite, aiohttp).
- Состояние задач только в SQLite; worker забирает работу из БД, а не из памяти.
- Скачивание клипа — строго после одобрения админа (модерация №1).
- Таймкоды субтитров берутся **только** из Whisper, никогда из LLM.
- Скачиваем только клипы ≤ 60 сек; исходник в кадре не кропаем и не зумим, свободное место закрываем размытой копией кадра.
- Субтитры: faster-whisper → постобработка → `.ass` (karаоке `\k`) → вшивание фильтром `ass=` в том же проходе ffmpeg.
- Ретраи тяжёлых шагов — до 3, затем `failed` + уведомление админу.
- Доступ к боту — только по ID администратора; один админ, один выходной «канал» (R2).
- Публикация в соцсети — вне scope v1.
- Секреты только в `.env`; поведение только в `config.yaml`.

## 8. Стиль кода

- Следовать структуре `src/shorteditor/<модуль>/`; не создавать новые верхнеуровневые пакеты без ADR.
- Публичные функции — с типами; внешние сервисы (Twitch, R2, Whisper) — за интерфейсами, чтобы подменять реализацию.
- Тесты: `pytest`, `pytest-asyncio`; на каждый модуль с логикой — unit-тесты, на конвейер — integration с замоканными внешними вызовами.
- Логи структурные (JSON-совместимые поля: `clip_id`, `stage`, `duration_ms`, `error`).
- Никаких «магических» констант: стиль субтитров, лимиты и таймауты — в `config.yaml`.

## 9. Чего делать нельзя

- Начинать разработку этапа, не отмеченного в журнале как `in_progress` тобой.
- Молча менять ТЗ: изменения только через раздел «Уточнения» в `docs/SPEC.md` + запись в `docs/DECISIONS.md`.
- Хардкодить токены, ID админа, пути к бакету.
- Оставлять после себя незакоммиченные изменения без записи в handoff.
