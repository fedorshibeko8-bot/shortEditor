# Журнал решений (ADR)

Формат: `D-XXX · дата · решение · контекст · следствия`.
Решения ниже считаются действующими. Менять их можно только новым ADR, который явно отменяет старый.

---

## D-001 · SQLite как единственный источник истины по клипам
**Дата:** 2026-11-25
**Решение:** состояния и очередь живут в SQLite (`aiosqlite`), worker забирает задачи запросом из БД.
**Контекст:** один админ, 3–5 видео/день, сервер 2 vCPU/4 GB; Redis/Celery избыточны.
**Следствия:** рестарт и `kill -9` не теряют задачи; нужен атомарный захват задачи (иначе двойная обработка); схеме нужны миграции.

## D-002 · Два гейта модерации, скачивание только после первого
**Дата:** 2026-11-25
**Решение:** `new → sent_to_admin → approved` и только потом скачивание; второй гейт — перед R2.
**Контекст:** экономия трафика и диска, контроль контента человеком.
**Следствия:** pipeline не может стартовать без `approved`; callback'и модерации должны быть идемпотентны.

## D-003 · Клипы только ≤ 60 сек, без тримминга
**Дата:** 2026-11-25 (уточнение U-1)
**Решение:** жёсткий фильтр парсера `duration ≤ 60`; обрезка на рендере не реализуется.
**Следствия:** нет логики выбора «лучшего» фрагмента; длина выхода = длина входа; в БД не нужны поля trim.

## D-004 · Исходник вписывается целиком, свободное место — размытой копией
**Дата:** 2026-11-25 (уточнение U-2)
**Решение:** `fit: contain`, без кропа и зума; фон — тот же кадр, растянутый на 1080×1920 и размытый (`gblur`).
**Следствия:** нет потери композиции; фильтр-граф сложнее, чем при кропе; нужно следить за цветовым сдвигом краёв при сильном blur.

## D-005 · Субтитры: Whisper → свой генератор `.ass` → libass
**Дата:** 2026-11-25 (уточнение U-6)
**Решение:** faster-whisper `medium`/`ru`/word timestamps; текст и таймкоды обрабатываем сами; `.ass` генерим своим кодом; вшиваем фильтром `ass=` в том же проходе ffmpeg.
**Контекст:** нужен karaoke по словам и полный контроль над таймингом.
**Следствия:** шрифты обязаны быть в образе (иначе libass подменит и метрики поедут); путь к `.ass` экранировать; snapshot-тесты на `.ass`.

## D-006 · LLM не участвует в таймкодах и не входит в v1
**Дата:** 2026-11-25 (уточнение U-7)
**Решение:** v1 — `initial_prompt` + словарь замен. LLM-нормализация текста — этап 5 за флагом, с инвариантом числа слов и фолбэком.
**Следствия:** интерфейс `normalize()` проектируем заранее, но не реализуем; тест «таймкоды не изменились» обязателен при включении.

## D-007 · Отказ действует на клип, автор не банится
**Дата:** 2026-11-25 (уточнение U-4)
**Решение:** `rejected` — только для конкретного `clip_id`; чёрный список авторов в v1 не ведём.
**Следствия:** нет таблицы банов; повторный клип того же автора снова может прийти (дедуп всё равно по `clip_id`).

## D-008 · «На переделку» в v1 — ограниченный набор правок
**Дата:** 2026-11-25 (уточнение U-3)
**Решение:** правка текста субтитров, karaoke on/off, текст хука. Перерендер из сохранённого транскрипта, без повторного ASR.
**Следствия:** транскрипт и версии рендера хранятся в БД; произвольный свободный текст правок машиной не исполняется.

## D-009 · Публикация = файл в R2, соцсети вне scope v1
**Дата:** 2026-11-25
**Решение:** `published` означает успешную загрузку в R2 + `meta.json`; автопостинг в TikTok/YT/Reels не делаем.
**Следствия:** критерий готовности v1 проверяется без внешних соцсетей; постинг — этап 5 с отдельным ADR по ToS.

## D-010 · Публичный репозиторий, секреты только локально
**Дата:** 2026-11-25
**Решение:** код и документация — в публичном GitHub-репозитории; `.env` и `config.yaml` в `.gitignore`; в репо только `*.example`.
**Следствия:** нельзя коммитить токены и ID админа; при утечке — ротация ключей Twitch/R2/бота.

## D-011 · Документация как протокол передачи контекста между агентами
**Дата:** 2026-11-25
**Решение:** `AGENTS.md` + `docs/HANDOFF.md` + `docs/TASKS.md` обязательны к обновлению в конце каждой сессии; задача имеет ID, владельца и критерии приёмки.
**Следствия:** накладные расходы на каждую сессию, зато нет «потерянных» полузадач; журнал истории append-only.

## D-012 · Лимит размера файла под Telegram Bot API
**Дата:** 2026-11-25
**Решение:** 45 МБ как предохранитель, ступенчатый `crf`, fallback на отправку документом.
**Контекст:** Bot API отдаёт файлы до 50 МБ, высокодетальный 60-секундный кадр может не влезть.
**Следствия:** после рендера выполняется контроль размера; при превышении используются CRF 24 и 28 максимум до двух повторов.

## D-013 · fps наследуется от исходника
**Дата:** 2026-11-25
**Решение:** `auto`, не выше 60; 30 — осознанный выбор для экономии рендера, а не дефолт «на всякий случай».
**Контекст:** исходная частота кадров задаётся в конфиге, а в рендере не используется жёсткое значение.
**Следствия:** для исходника 60 fps допустим даунсемпл до 30 без изменения выбранного поведения в коде.
**Реализация схемы:** в Python `fps` представлен как `Literal["auto"] | int` с валидацией целого значения от 1 до 60.

## D-014 · TTL карточек модерации
**Дата:** 2026-11-25
**Решение:** 24 ч, авто-`rejected` с причиной `expired`; карточка редактируется с убранными кнопками.
**Контекст:** иначе очередь и чат забиваются старыми карточками.
**Следствия:** просроченные клипы не блокируют очередь и отдельно учитываются в сводке.

## D-015 · Ретеншн мастеров 180 дней
**Дата:** 2026-11-25
**Решение:** lifecycle-правило бакета, настраивается вручную; код ретеншном не управляет.
**Контекст:** мастера должны удаляться автоматически через заданный срок хранения.
**Следствия:** дефолтная длительность хранения — 180 дней; реализация задаётся конфигурацией бакета вне кода.

## D-016 · Fallback Whisper по качеству, а не по времени
**Дата:** 2026-11-25
**Решение:** триггеры из §3.4 v1.2; fallback не более одного раза на клип.
**Контекст:** качество распознавания оценивается по метрикам результата, а не по длительности попытки.
**Следствия:** после неудачного fallback клип уходит в `failed`; повторный fallback не выполняется.

## D-017 · Один контейнер на v1 (bot+worker+scheduler в одном процессе)
**Дата:** 2026-11-25
**Решение:** на v1 бот, worker и scheduler запускаются в одном контейнере и одном процессе.
**Контекст:** SQLite — единственный источник истины, сервер располагает 2 vCPU / 4 GB RAM, параллельность рендера ограничена одним.
**Следствия:** отдельные процессы/контейнеры рассматриваются при переходе на внешнюю очередь.
